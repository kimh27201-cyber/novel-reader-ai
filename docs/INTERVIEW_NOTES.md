## 30 秒项目介绍

> 我做的是一个 AI 阅读助手系统，前端用 uni-app，后端用 FastAPI。后端实现了用户注册登录、JWT 鉴权、书架和章节管理、阅读记录、动态书源解析、AI 总结问答、历史记录和 AI 调用日志。项目还补了 pytest、Alembic 迁移、GitHub Actions CI、Docker 配置、统一错误响应、request_id 日志和 AI provider 异常分类，主要用来展示我对 Python 后端、数据库、接口测试和前后端联调的完整实践。

## 2 分钟项目介绍

可以按这个结构讲：

1. **背景**：我想做一个能体现 Python 后端和 AI 应用能力的完整项目，所以选择了阅读助手这个场景。
2. **后端能力**：FastAPI 负责接口，SQLAlchemy 负责模型和数据库，JWT 做登录鉴权，pytest 覆盖核心接口。
3. **业务闭环**：用户登录后可以维护书架、章节和阅读进度，也可以导入演示书源，搜索、解析目录和正文。
4. **AI 能力**：阅读器可以调用 AI 总结章节或进行问答，后端会保存总结、问答历史和 AI 调用日志。默认 mock 模式保证没有 API Key 也能演示。
5. **工程化**：项目接入 Alembic、Docker、GitHub Actions、统一错误响应和 request_id 日志，方便迁移、部署、测试和排查问题。
6. **前端联调**：uni-app 页面接入了后端登录、云端书架、书源搜索、阅读器和 AI 记录，AI 记录页可以查看总结、问答和调用日志。

## 项目亮点

- **完整性**：不是单个接口 demo，而是包含登录、业务数据、AI 功能、测试、CI 和文档的完整项目。
- **可演示**：没有真实 AI Key 也能通过 mock 模式展示完整流程。
- **有测试**：后端 pytest 覆盖多类业务和异常场景，前端工具测试覆盖书源引擎、API client、后端适配层和 AI 历史。
- **可维护**：使用 Alembic 管理迁移，统一错误响应减少前端错误处理分支。
- **可排查**：每个请求都有 `X-Request-ID`，方便把前端报错、Swagger 调试和后端日志关联起来。
- **AI 健壮性**：AI provider 超时、上游错误和返回格式异常会被分类处理，成功和失败都会写入 AI 调用日志。
- **合规意识**：不内置盗版书源，不绕过付费或登录规则，只做工具和演示源。

## 面试常见追问

### 为什么选择 FastAPI？

FastAPI 写接口效率高，天然支持 Pydantic 数据校验和 OpenAPI 文档，适合做前后端联调和 Swagger 演示。它也支持 async，后续接 AI API 或网络解析时更方便。

### JWT 鉴权怎么做？

用户登录成功后，后端用用户 id 生成 JWT，前端保存 token。访问受保护接口时，前端在 `Authorization: Bearer <token>` 中携带 token，后端解析 token 得到当前用户，再基于当前用户做数据隔离。

### 用户数据怎么隔离？

书籍、书源、AI 记录等表都有 `user_id`。查询或修改时不会只按资源 id 查，而是同时校验资源是否属于当前登录用户。例如获取章节时，会通过章节关联的书籍检查书籍归属。

### 为什么要做统一错误响应？

默认 FastAPI 错误结构在不同异常下不完全一致。统一错误响应后，前端可以稳定读取 `error.message` 做提示，也可以通过 `error.request_id` 找到后端对应日志。为了兼容旧逻辑，我保留了原来的 `detail` 字段。

### request_id 有什么用？

当用户反馈“接口报错”时，前端或 Swagger 响应里能看到 `X-Request-ID`。后端日志也会打印同一个 request_id，这样可以快速定位同一次请求的路径、状态码、耗时和异常。

### 为什么需要 Alembic？

`create_all` 适合早期快速建表，但项目迭代后需要可追踪的数据库结构变更。Alembic 可以把数据库结构变化记录成迁移文件，方便本地、CI 和部署环境保持一致。

### 你的测试覆盖了什么？

后端测试覆盖了注册登录、鉴权、用户数据隔离、书架章节、阅读历史、书源导入解析、AI 总结问答、AI 调用日志、数据库配置、CORS、迁移文件和统一错误响应。前端 Node 测试覆盖了书源引擎、API client、后端数据适配和 AI 历史。

### AI 接口没有真实 Key 怎么演示？

项目默认使用 mock provider，返回稳定的总结和问答结果。这样 CI、本地演示和面试现场都不依赖真实 API Key。后续可以通过环境变量切换到真实 provider。真实 provider 超时、上游错误或返回格式异常时，后端会返回统一错误响应，并把失败写入 AI 调用日志。

### 项目下一步怎么优化？

可以继续做三类优化：

- AI 调用健壮性：超时、重试、错误分类、调用记录
- 前端体验：加载态、空状态、错误提示、移动端细节
- 部署展示：Docker 云服务器部署、README 截图、录屏演示
